# `db/` — schema, migrations, roles, seeds

This backend owns the schema outright (ADR-017 §3.1): nothing else connects to this
database, so the schema, the models that reflect it, and the code that uses it are one
repository, reviewed as one change.

## Layout

```
db/
  baseline/00001_baseline.sql   the design baseline, applied verbatim — never autogenerated,
                                 never rewritten into ORM calls (database spec §8.3)
  versions/                     Alembic revisions (20260926_0001_baseline.py applies the file above)
  seeds/reference.sql           platform reference data (roles, permissions, features, plans,
                                 quotas, measurement_fields) — idempotent, every environment
  seeds/demo.sql                local-only fake data — refused in production, see below
  roles/                        app_user.sql, app_worker.sql, app_migrator.sql — one-time,
                                 per-environment role bootstrap for anything that isn't the
                                 local Docker Compose setup (see "Roles" below)
  tests/                        rls_isolation.sql, constraints.sql, explain_regression.sql
                                 (built in M1 — the isolation suite must exist before any
                                 business module, per the implementation plan)
```

## Roles — why there are two ways to set them up

Three roles run this database (ADR-001, ADR-003, ADR-010):

| Role | Used by | Statement timeout | Table ownership |
|---|---|---|---|
| `app_migrator` | Alembic, CI, one-time bootstrap | none (DDL) | owns everything it creates |
| `app_user` | the running API | 5 s | owns nothing, no `BYPASSRLS` |
| `app_worker` | the background worker | 120 s | owns nothing, member of `app_user` |

The baseline migration (`db/versions/20260926_0001_baseline.py`) creates `app_user` and `app_worker`
as `NOLOGIN` with every grant and RLS policy they need — that part is schema, reviewed once,
committed to git. It never sets a password, because a password is a secret and secrets do
not belong in a versioned SQL file.

**Local Docker Compose** sidesteps the chicken-and-egg problem of "who creates
`app_migrator` before it exists to run the baseline": `docker-compose.yml` sets
`POSTGRES_USER=app_migrator`, so the official `postgres` image creates it as the bootstrap
superuser on first start. The first migration then reads `APP_USER_PASSWORD` and
`APP_WORKER_PASSWORD` from the environment and sets them with `ALTER ROLE ... LOGIN
PASSWORD` right after applying the baseline — one command (`alembic upgrade head`) leaves
you with a fully working, loginable set of roles. This is why `db/roles/*.sql` are not
needed locally.

**Every other environment** (Supabase, a bare PostgreSQL instance) does not get that
free bootstrap. There, an administrator runs, once, in this order:

1. `db/roles/app_migrator.sql` — as whatever admin connection the provider gives you.
2. `alembic upgrade head`, connected as `app_migrator` (`MIGRATION_DATABASE_URL`).
3. `db/roles/app_user.sql` and `db/roles/app_worker.sql` — as `app_migrator` (it holds
   `CREATEROLE`) or the same admin connection.

Each file takes a `password` psql variable and is never given a real value in git; it is
supplied at run time from whatever secret manager the environment uses.

## Reseeding reference data

`db/seeds/reference.sql` is the same content already inside the baseline (section 17
there), extracted so it can be re-applied on its own — every statement is
`ON CONFLICT ... DO NOTHING`, so running it twice, or after the baseline already ran it
once, changes nothing. Useful in CI, or when provisioning a new environment from an
already-migrated snapshot.

## Demo data

`db/seeds/demo.sql` is deliberately a placeholder in M0. See the comment inside it: a
demo tenant needs the same provisioning transaction a real signup gets (WF-01), and hand
writing that in SQL would duplicate business logic that belongs in
`modules/identity` — this file becomes real once that module exists (M1).
